## Code Generation Rules

These rules were developed against Gemini failure modes but represent sound general practices.
Include them in the Codex prompt. They may or may not catch Codex-specific issues — the goal
is to carry forward what we know while staying alert to new patterns.

| # | Rule |
|---|---|
| F1 | **`enabled` guard on conditional queries** — any `useQuery` only valid for a specific role/state must pass `enabled: <boolean>`. Never fire unconditionally. |
| F2 | **QueryClientProvider placement** — never call hooks in the same component that provides `QueryClientProvider`. Split into outer provider + inner consumer. |
| F3 | **StrictMode double-invoke guard** — `useEffect` that calls a mutating API must be guarded with `useRef(false)`. React 18 double-invokes effects in development. |
| F4 | **Use shared types** — never redeclare inline types for API payloads. Import from `@mysitter/types`. |
| F5 | **Verify field existence before use** — confirm every field exists in the canonical type or Pydantic schema before referencing it. |
| F6 | **No stub onClick/onPress** — every handler must be implemented. Disable or remove buttons that aren't ready. |
| F7 | **All imports must be used** — no unused imports. |
| F8 | **Match JSX opening/closing tags** — triple-check casing on closing tags. |
| F9 | **ApiClient namespaces are class properties** — object literals, not methods. |
| F10 | **Object params, not positional** — always match the TypeScript signature. |
| F11 | **Mobile uses relative imports** — no `@/` alias in `apps/mobile`. |
| F12 | **Verify mobile export names against source** — don't assume they match the web app. |
| B1 | **SQLAlchemy 2.x count pattern** — `select(func.count()).select_from(q.subquery())`. |
| B2 | **Never import from the app entry point in routers** — shared infra belongs in `app/core/`. |
| B3 | **Never access model attributes not in the model definition** — check `Mapped` columns before referencing. |
| B4 | **No bare `pass` in stubs** — always `raise NotImplementedError(...)`. |
| B5 | **No `__import__()`** — top-of-file imports only. |
| B6 | **No dead branches** — no `if False:`, `if True:`, or unreachable arms. |
| B7 | **Account for all downstream resource creation** — creation flows must handle related rows. |
| T1 | **Test fixtures must match endpoint response schema** — verify fields exist in `response_model` before reading them. |
| T2 | **Use real dependencies in integration tests** — no mocking the database. |
| I1 | **Follow the file layout in the plan exactly** — no extra directories or parallel implementations. |
| I2 | **Include all required system dependencies in Dockerfiles** — check for `gdal-bin`, `libpq-dev`, etc. |
| I3 | **Use the correct CI platform** — this project uses GitLab CI (`.gitlab-ci.yml`), not GitHub Actions. |

## Step 1 — Sentry Observability

**Goal:** Capture unhandled exceptions and performance traces in production across all three
surfaces: API, web, and mobile. Without this, production errors are invisible.

### 1a. API — `sentry-sdk`

**Add to `apps/api/requirements.txt`:**
```
sentry-sdk[fastapi]==2.*
```

**`apps/api/app/core/config.py`** — add setting:
```python
sentry_dsn: str | None = None
```

**`apps/api/app/main.py`** — initialize before the app is created:
```python
import sentry_sdk
from sentry_sdk.integrations.fastapi import FastApiIntegration
from sentry_sdk.integrations.celery import CeleryIntegration

if settings.sentry_dsn:
    sentry_sdk.init(
        dsn=settings.sentry_dsn,
        integrations=[FastApiIntegration(), CeleryIntegration()],
        traces_sample_rate=0.2,
        environment=settings.environment,
    )
```

Add `SENTRY_DSN` and `ENVIRONMENT` (e.g. `"production"` / `"development"`) to
`.env.production.example`.

`CeleryIntegration` captures errors from Celery tasks automatically — no extra
instrumentation needed in `tasks.py`.

`traces_sample_rate=0.2` captures 20% of requests for performance monitoring. Adjust
based on traffic volume.

### 1b. Web — `@sentry/react`

**Add to `apps/web/package.json` dependencies:**
```
"@sentry/react": "^8"
```

**`apps/web/src/main.tsx`** — initialize before `ReactDOM.createRoot`:
```typescript
import * as Sentry from "@sentry/react";

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  environment: import.meta.env.VITE_ENV ?? "development",
  integrations: [
    Sentry.browserTracingIntegration(),
    Sentry.replayIntegration({ maskAllText: false, blockAllMedia: false }),
  ],
  tracesSampleRate: 0.2,
  replaysSessionSampleRate: 0.05,
  replaysOnErrorSampleRate: 1.0,
});
```

Add `VITE_SENTRY_DSN` and `VITE_ENV` to `apps/web/.env.example`.

Wrap the root component in `Sentry.ErrorBoundary` in `main.tsx`:
```tsx
root.render(
  <Sentry.ErrorBoundary fallback={<p>Something went wrong.</p>}>
    <App />
  </Sentry.ErrorBoundary>
);
```

### 1c. Mobile — `@sentry/react-native`

**Add to `apps/mobile/package.json` dependencies:**
```
"@sentry/react-native": "^6"
```

**`apps/mobile/app/_layout.tsx`** — initialize at the top, before any hooks:
```typescript
import * as Sentry from "@sentry/react-native";

Sentry.init({
  dsn: process.env.EXPO_PUBLIC_SENTRY_DSN,
  environment: process.env.EXPO_PUBLIC_ENV ?? "development",
  tracesSampleRate: 0.2,
});
```

Add `EXPO_PUBLIC_SENTRY_DSN` and `EXPO_PUBLIC_ENV` to `apps/mobile/.env.example`
(create if absent).

> **Note on mobile imports:** Use `@sentry/react-native` directly — not `@sentry/expo`
> (deprecated). All imports in `_layout.tsx` must remain relative or use package names
> directly — no `@/` alias.

### 1d. Verify Sentry DSN handling

In all three surfaces, the Sentry DSN must be **optional** — if the env var is absent or
empty, the SDK must not be initialized and the app must still start normally. This ensures
local development works without a Sentry account. The API config field is already
`str | None = None`; the web/mobile init calls only fire when the DSN var is truthy (the
SDK handles a missing DSN gracefully, but an explicit guard is clearer):

```typescript
// Web / Mobile — only init if DSN is set
if (import.meta.env.VITE_SENTRY_DSN) {
  Sentry.init({ ... });
}
```

## Step 2 — Playwright E2E Tests

**Goal:** Browser-level tests that verify the web app's critical paths end-to-end, from the
perspective of a real user clicking through the UI. Unit and integration tests cover the API;
Playwright covers the full stack including routing, form submission, and real HTTP calls.

### Setup

**Add to `apps/web/package.json` devDependencies:**
```
"@playwright/test": "^1.44"
```

**New file: `apps/web/playwright.config.ts`**

export default defineConfig({

  fullyParallel: true,

  retries: process.env.CI ? 2 : 0,
  reporter: "html",
  use: {

  projects: [

  ],
  webServer: {
    command: "npm run dev",

### Test infrastructure notes

- E2E tests run against a **live dev server** (`npm run dev`) pointed at a **real API**
  (`http://localhost:8000`). They are not mocked. The API must be running for the tests
  to pass.
- Each test that requires authentication should use Playwright's `storageState` to cache
  a logged-in session rather than re-logging in on every test. Create a
  `apps/web/e2e/fixtures/auth.ts` global setup file that registers a test user once and
  saves the auth token to local storage.
- Do not hardcode provider or booking UUIDs — either create them during test setup or
  skip tests that require seeded data with `test.skip`.

### GitLab CI update

Add a second job to `.gitlab-ci.yml` that runs Playwright:

```yaml
e2e-tests:
  stage: test
  image: mcr.microsoft.com/playwright:v1.44.0-jammy
  before_script:
    - cd apps/web && npm ci
  script:
    - npx playwright test
  artifacts:
    when: on_failure
    paths:
      - apps/web/playwright-report/
    expire_in: 7 days
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == "main"'
```

> **Note:** Playwright E2E tests require the API to be running. In CI, either start the API
> as a background service in this job, or mark E2E as a manual/scheduled pipeline stage
> rather than blocking every MR. The simpler first step is `when: manual` so they can be
> triggered on demand without blocking the fast `api-tests` job.

## Step 3 — Load Test Suite

**Goal:** Expand the placeholder `load_tests/locustfile.py` into a realistic multi-user
simulation that can identify bottlenecks before they appear in production.

### What the current file does

The existing `locustfile.py` only tests:
- `GET /providers/search` (unauthenticated, hardcoded lat/lng)
- `GET /providers/{id}` (hardcoded UUID `00000000-...001`)
- `GET /bookings` (authenticated, but token is from a hardcoded test account)

It has no provider simulation, no booking creation, no messaging, and no setup/teardown.
Replace it entirely.

### New `load_tests/locustfile.py`

Define two user classes: `CustomerUser` and `ProviderUser`. Each registers a unique account
in `on_start` using a random suffix (so parallel workers don't collide) and then exercises
their respective flows.

**`CustomerUser` tasks:**
```python
@task(5)
def search_providers(self):
    # GET /providers/search with lat/lng near NYC
    
@task(2)  
def view_provider_profile(self):
    # GET /providers/{id} — use a provider ID discovered during search
    
@task(1)
def create_booking(self):
    # POST /bookings — only if self.provider_id is set from a prior search
    
@task(2)
def list_my_bookings(self):
    # GET /bookings
    
@task(1)
def list_conversations(self):
    # GET /conversations
```

**`ProviderUser` tasks:**
```python
@task(3)
def list_my_bookings(self):
    # GET /bookings (provider sees their incoming bookings)

@task(1)
def confirm_pending_booking(self):
    # PATCH /bookings/{id}/confirm — if a PENDING booking exists

@task(2)
def check_analytics(self):
    # GET /analytics/me — skip if 402 (BASIC tier)
```

**`on_start` pattern for both:**
```python
def on_start(self):
    suffix = uuid.uuid4().hex[:8]
    resp = self.client.post("/auth/register", json={
        "email": f"loadtest_{suffix}@example.com",
        "password": "LoadTest1!",
        "display_name": f"Load User {suffix}",
        "role": "CUSTOMER",  # or "PROVIDER"
    })
    if resp.status_code == 201:
        self.token = resp.json()["access_token"]
        self.headers = {"Authorization": f"Bearer {self.token}"}
    else:
        self.token = None
        self.headers = {}
```

### New `load_tests/locust.conf`

## Post-Review: Codex Comparison Notes

*(Fill in after Claude reviews the Codex output)*

### What Codex got right
- **0 missing files** — all 19 files from the plan were produced. Gemini routinely skips infrastructure steps; Codex did not.
- Sentry DSN guards are correctly optional on all three surfaces (API `str | None = None`, web/mobile `if DSN:` guard).
- `_layout.tsx` Sentry init is at module level before any hooks or component definitions.
- Playwright `globalSetup` pattern is correctly wired: registers customer + provider via API, writes `localStorage` auth token to `.auth/` JSON, each spec loads it via `test.use({ storageState })`.
- `on_start` uses a random UUID suffix — parallel Locust workers won't collide on email uniqueness.
- `confirm_pending_booking` in locust correctly uses `POST` (matching `@router.post("/{booking_id}/confirm")`), even though the plan spec said PATCH. Codex apparently read the actual codebase rather than just the plan.
- `e2e-tests` CI job set to `when: manual` per the plan's recommendation.
- No hardcoded provider or booking UUIDs — uses `test.skip` when no seed data exists.
- No over-engineering or parallel implementations.

### What Codex got wrong / new failure patterns
- **UTF-16 file encoding on `requirements.txt`** — Codex wrote the file with a UTF-16 BOM (`file` command: "Unicode text, UTF-16, little-endian text"). pip cannot parse this format and would fail silently or crash. Fixed by re-encoding to UTF-8.
- Minor PEP 8 lapse: missing blank line between the Sentry init block and `@asynccontextmanager` in `main.py`. Fixed.

### New rules to add to `CODEX_CODING_STANDARDS.md`
- **C1: Verify text file encoding** — After any file is generated, check encoding with `file <path>`. If it reports UTF-16, re-encode to UTF-8. Particularly important for `requirements.txt`, `.env*`, and any file that pip or a build tool parses as plain text.
- **C2: Codex may use the actual codebase as ground truth when it disagrees with the plan** — this is generally good (e.g. using `POST` for confirm when plan said `PATCH`) but should be verified by reading the actual endpoint definition. Trust the code over the plan spec.

### Overall assessment vs Gemini for this type of task
Codex significantly outperformed Gemini for infrastructure/observability/test-tooling tasks:
- **Coverage:** 0 missing files vs Gemini's pattern of skipping CI/infrastructure steps entirely.
- **Bug count:** 1 critical (file encoding artifact) + 1 minor (PEP 8) vs Gemini's typical 3–9 logic/import/architecture bugs.
- **Adherence to spec:** Codex followed the plan file layout exactly, no parallel implementations or unsolicited gold-plating.
- **Test quality:** Playwright fixture/storageState design is notably well-structured; Locust user class separation is clean.

The UTF-16 encoding bug is a Codex sandbox artifact (not a logic error), making it mechanically detectable and fixable. Gemini's bugs tend to be logic, import, or architecture errors that require deeper reasoning to identify and fix.
