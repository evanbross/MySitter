## Step 1 — Environment Bootstrap


Then start Docker: `docker-compose up -d`

Verify: `docker exec mysitter_postgres pg_isready -U mysitter`

**Why first:** Pydantic Settings raises on startup without `SECRET_KEY`. Every subsequent step requires a running DB and Redis.

## Step 4 — Wire Redis into AuthService (Passkey Challenge Store)

**Goal:** Complete the passkey auth flow end-to-end. This is the biggest backend gap.

### 4a — Add async Redis client

Create `apps/api/app/core/redis.py`:

```python
from redis.asyncio import Redis as AsyncRedis
from app.core.config import settings

redis_client: AsyncRedis = AsyncRedis.from_url(settings.redis_url, decode_responses=False)
```

> **Important:** Module-level singleton — do NOT create per request. `redis.asyncio.Redis` is connection-pool-backed; recreating per request leaks connections.

Add `get_redis()` to `apps/api/app/core/deps.py`:

```python
from app.core.redis import redis_client
from redis.asyncio import Redis as AsyncRedis

async def get_redis() -> AsyncGenerator[AsyncRedis, None]:
    yield redis_client
```

Add `redis: AsyncRedis = Depends(get_redis)` to the passkey endpoints in `apps/api/app/routers/auth.py`.

### 4b — Implement challenge store in `auth_service.py`

Challenge key naming:
- Registration: `passkey_challenge:reg:{user_id}` (5-minute TTL)
- Authentication: `passkey_challenge:auth:{email}` (5-minute TTL)

Store challenge bytes as base64-encoded string: `await redis.setex(key, 300, base64.b64encode(challenge))`

Retrieve and delete after use (prevents replay).

### 4c — Implement `verify_passkey_auth` (currently raises 501)

Full flow:
1. Extract `credential_id` from `credential_json["id"]` (base64url-encoded), decode to bytes
2. Query `passkey_credentials` by `credential_id` bytes, join to `users`
3. Retrieve stored challenge from Redis using `passkey_challenge:auth:{email}`
4. Call `webauthn.verify_authentication_response` with the real public key and sign count
5. On success: update `sign_count` and `last_used_at` in DB, delete challenge from Redis, issue tokens

> **Note:** Use `redis.asyncio` (included in the `redis` package v5.x already installed). Do NOT install `aioredis` separately.

## Step 6 — Fix Register Contract Mismatch

**File:** `packages/api-client/src/client.ts`

**Problem:** `auth.register()` is typed as returning `User`, but the backend returns `TokenPair`. `RegisterPage` calls `tokens.access_token` on the result, which silently fails.

**Fix:** Change the `register` return type to `TokenPair`:

```typescript
register: (data: UserCreate) =>
  this.request<TokenPair>("POST", "/auth/register", data, true),
```

This matches how `auth.login` is already typed.

## Step 7 — Add TOTP Prompt to LoginPage

**File:** `apps/web/src/pages/auth/LoginPage.tsx`

**Problem:** Backend returns HTTP 422 with `detail: "TOTP code required"` when a TOTP-enabled user logs in without a code. The current UI has no TOTP input — those users are permanently locked out.

**Fix:** Two-step form:
1. First submit: email + password
2. If response is 422 with `"TOTP code required"`, show a TOTP input field
3. Second submit: email + password + TOTP code

The `useAuth` hook already passes `totpCode` through to `apiClient.auth.login` — only the form UI needs updating.

## Step 8 — Add Passkey Login UI

**Files:** New `apps/web/src/hooks/usePasskeyAuth.ts`, updated `LoginPage.tsx`

**Flow:**
1. User enters email, clicks "Sign in with passkey"
2. Call `apiClient.auth.getPasskeyAuthOptions(email)` → `PublicKeyCredentialRequestOptions`
3. Pass to `@simplewebauthn/browser`'s `startAuthentication(options)`
4. POST result to `apiClient.auth.verifyPasskeyAuth(credential)`
5. On success: store `access_token`, navigate to dashboard

Create `usePasskeyAuth` hook using `useMutation` from TanStack Query (consistent with `useAuth` pattern).

> **Use `@simplewebauthn/browser`** — already in `package.json`. Do not call the raw `navigator.credentials` API directly; the library handles base64url encoding, browser quirks, and error normalization.

> **Note:** Cannot be tested end-to-end until Step 4 (Redis challenge store) is complete.

## Key Architecture Decisions (do not second-guess these)

- **Redis client is a module-level singleton** — connection-pool-backed, do not recreate per request
- **Passkey challenge TTL is 5 minutes** — matches WebAuthn spec recommendation; shorter breaks slow connections, longer widens replay window
- **Challenges stored server-side in Redis** — never in JWT or signed cookie; must be opaque to client
- **Credential lookup during auth is a direct DB query** by raw `credential_id` bytes — `passkey_credentials.credential_id` stores raw bytes (`LargeBinary`), joined to `users`
- **Celery tasks are synchronous** — use `DATABASE_SYNC_URL` + synchronous `sessionmaker` inside workers; do not mix Celery with async SQLAlchemy
