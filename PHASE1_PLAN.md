```python
from app.models.user import User  # add import

async def search(self, lat, lng, radius_miles, service_type, page):
    radius_m = radius_miles * _MILES_TO_METERS
    point_wkt = f"SRID=4326;POINT({lng} {lat})"

    base_q = (
        select(
            ProviderProfile,
            User.display_name,
            User.avatar_url,
            func.ST_Distance(
                ProviderProfile.location,
                func.ST_GeogFromText(point_wkt),
            ).label("dist_m"),
        )
        .join(User, User.id == ProviderProfile.user_id)
        .where(ProviderProfile.is_active.is_(True))
        .where(
            ST_DWithin(
                ProviderProfile.location,
                func.ST_GeogFromText(point_wkt),
                radius_m,
            )
        )
    )
    if service_type:
        base_q = base_q.where(service_type == any_(ProviderProfile.services))

    count_q = select(func.count()).select_from(base_q.subquery())
    total = await self._db.scalar(count_q)

    rows_q = base_q.order_by("dist_m").offset((page - 1) * 20).limit(20)
    rows = (await self._db.execute(rows_q)).all()

    items = []
    for profile, display_name, avatar_url, dist_m in rows:
        item = ProviderSearchResult.model_validate(profile)
        item.display_name = display_name
        item.avatar_url = avatar_url
        item.distance_miles = round(dist_m / _MILES_TO_METERS, 2)
        items.append(item)

    return PaginatedProviderSearch(
        items=items, total=total or 0, page=page, page_size=20,
        has_next=len(items) == 20,
    )
```

    user: User,
    booking: Booking,

**Fix `confirm()` to require PROVIDER role:**

```python
async def confirm(self, user: User, booking_id: uuid.UUID) -> Booking:
    if user.role != UserRole.PROVIDER:
        raise HTTPException(status_code=403, detail="Only providers can confirm bookings")
    booking = await self.get_for_user(user, booking_id)
    if booking.status != BookingStatus.PENDING:
        raise HTTPException(status_code=409, detail="Booking is not pending")
    await self._check_conflicts(booking.provider_id, booking.start_at, booking.end_at, booking.id)
    booking.status = BookingStatus.CONFIRMED
    await self._db.commit()
    return booking
```

**Add `_check_conflicts`:**

```python
async def _check_conflicts(
    self, provider_id: uuid.UUID, start_at: datetime, end_at: datetime,
    exclude_booking_id: uuid.UUID | None = None,
) -> None:
    q = select(Booking).where(
        Booking.provider_id == provider_id,
        Booking.status == BookingStatus.CONFIRMED,
        Booking.start_at < end_at,
        Booking.end_at > start_at,
    )
    if exclude_booking_id:
        q = q.where(Booking.id != exclude_booking_id)
    if await self._db.scalar(q):
        raise HTTPException(status_code=409, detail="Provider has a conflicting confirmed booking")
```

Note: conflict checking for recurring bookings is done at the `BookingOccurrence` level in the Celery task (Step 6), not here.

**Why before frontend booking flow (Step 8):** The booking creation and confirm flows must be correct before building the UI on top of them.

## Step 6 — Implement `expand_recurring_bookings` Celery Task

**Goal:** Replace the stub task with a real implementation that generates `BookingOccurrence` rows for all confirmed recurring bookings, rolling 8 weeks ahead, idempotently.

**Files to modify:**
- `apps/api/app/workers/tasks.py`
- `apps/api/requirements.txt` (add `python-dateutil>=2.9` explicitly)

**Implementation:**

```python
@celery_app.task
def expand_recurring_bookings() -> None:
    """
    For every CONFIRMED recurring booking, generate BookingOccurrence rows
    for the next 8 weeks. Safe to run multiple times — skips existing occurrences.
    Uses synchronous SQLAlchemy — Celery workers have no event loop.
    """
    from datetime import timezone
    from dateutil.rrule import rrulestr
    from sqlalchemy import create_engine
    from sqlalchemy.orm import Session as SyncSession

    engine = create_engine(settings.database_sync_url)
    horizon = datetime.now(timezone.utc) + timedelta(weeks=8)

    with SyncSession(engine) as session:
        recurring = session.scalars(
            select(Booking).where(
                Booking.rrule_string.isnot(None),
                Booking.status == BookingStatus.CONFIRMED,
            )
        ).all()

        for booking in recurring:
            rule = rrulestr(booking.rrule_string, dtstart=booking.start_at)
            duration = booking.end_at - booking.start_at
            existing = {
                occ.scheduled_at
                for occ in session.scalars(
                    select(BookingOccurrence).where(BookingOccurrence.booking_id == booking.id)
                )
            }
            for dt in rule.between(datetime.now(timezone.utc), horizon, inc=True):
                if dt not in existing:
                    session.add(BookingOccurrence(
                        booking_id=booking.id,
                        scheduled_at=dt,
                        status=BookingStatus.CONFIRMED,
                    ))
        session.commit()
    engine.dispose()
```

Also wire `expand_recurring_bookings.delay()` to be called from `BookingService.confirm()` when `booking.rrule_string is not None` — so occurrences are generated immediately on confirm, not just from the daily beat.

**Why after Step 5:** The task only processes CONFIRMED bookings. The confirm logic must be correct first.

## Key Architecture Decisions — Do Not Second-Guess These

1. **Provider activation is gated on subscription.** `ProviderProfile.is_active` is set to `False` at creation and only flipped to `True` by the Stripe `invoice.paid` webhook. Providers are invisible in search until they subscribe. Do not add a bypass or free tier without a deliberate design decision.

2. **Search returns the paginated envelope — always.** The frontend API client types search as `PaginatedResponse<ProviderSearchResult>`. The API was wrong (returning a plain list); Step 2 makes the API conform to the client's expectation.

3. **`booking.provider_id` is a `ProviderProfile.id`, not a `User.id`.** The `BookingResponse` schema exposes `provider_id` as a `ProviderProfile.id`. Any UI that needs the provider's `display_name` must either join or make a second API call with `useProviderProfile(provider_id)`.

4. **Only the assigned provider can confirm a booking.** Enforced at the service layer in `BookingService.confirm()`. Customers cannot confirm their own bookings.

5. **Celery tasks are strictly synchronous.** `expand_recurring_bookings` and all notification tasks use `create_engine(settings.database_sync_url)` + synchronous `Session`. Never use `AsyncSession` inside a Celery task.

6. **Stripe webhooks require raw request body.** The `/billing/webhook` endpoint uses `await request.body()` directly. Never declare a Pydantic body model on the webhook route — FastAPI's body parsing consumes the stream and breaks Stripe signature verification.

7. **Mapbox public token (`pk.`) only in the frontend.** `VITE_MAPBOX_TOKEN` uses the public token (starts with `pk.`), not the secret token (`sk.`). The secret token is for server-side geocoding only (a later phase concern).

8. **FullCalendar rrule strings are passed through verbatim.** The rrule string from the API (`FREQ=WEEKLY;BYDAY=MO`) is passed directly to FullCalendar's `rrule` event property — FullCalendar handles expansion via `@fullcalendar/rrule`. The frontend never expands rrules manually.

9. **No new Alembic migration needed for Phase 1.** All tables (`provider_profiles`, `availability`, `subscriptions`, `bookings`, `booking_occurrences`) were created in the Phase 0 initial migration. Phase 1 adds no new columns or tables. `service_area: Geography(POLYGON)` is deferred to Phase 3.

10. **`python-dateutil` must be explicit in `requirements.txt`.** The Celery task uses `dateutil.rrule.rrulestr()`. While it's a transitive dependency of Celery, add `python-dateutil>=2.9` explicitly — transitive dependencies can silently disappear on version bumps.
