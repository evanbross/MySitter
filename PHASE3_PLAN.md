**`review_service.py` — key methods:**

```python
class ReviewService:
    def __init__(self, db: AsyncSession) -> None:
        self._db = db

    async def create(
        self, user: User, booking_id: uuid.UUID, body: ReviewCreateRequest
    ) -> Review:
        # 1. Load booking, assert it is COMPLETED
        booking = await self._db.get(Booking, booking_id)
        if not booking or booking.status != BookingStatus.COMPLETED:
            raise HTTPException(400, "Can only review completed bookings")

        # 2. Assert reviewer is a participant
        provider_profile = await self._db.scalar(
            select(ProviderProfile).where(ProviderProfile.id == booking.provider_id)
        )
        if user.id not in (booking.customer_id, provider_profile.user_id):
            raise HTTPException(403, "Not a participant in this booking")

        # 3. Determine reviewee: if reviewer is customer, reviewee is provider's user; vice versa
        reviewee_id = (
            provider_profile.user_id
            if user.id == booking.customer_id
            else booking.customer_id
        )

        review = Review(
            booking_id=booking_id,
            reviewer_id=user.id,
            reviewee_id=reviewee_id,
            rating=body.rating,
            body=body.body,
        )
        self._db.add(review)
        await self._db.flush()  # get id before updating aggregate
        await self._recalculate_provider_rating(booking.provider_id)
        await self._db.commit()
        return review

    async def _recalculate_provider_rating(self, provider_profile_id: uuid.UUID) -> None:
        """Recompute rating + review_count from reviews where reviewee is the provider's user."""
        profile = await self._db.get(ProviderProfile, provider_profile_id)
        result = await self._db.execute(
            select(func.avg(Review.rating), func.count(Review.id))
            .join(Booking, Review.booking_id == Booking.id)
            .where(Booking.provider_id == provider_profile_id)
            # Only count customer→provider reviews (not provider→customer)
            .where(Review.reviewer_id == Booking.customer_id)
        )
        avg_rating, count = result.one()
        profile.rating = round(float(avg_rating), 2) if avg_rating else 0.0
        profile.review_count = count or 0

    async def list_for_provider(
        self, provider_profile_id: uuid.UUID, page: int = 1, page_size: int = 20
    ) -> tuple[list[Review], int]:
        base_q = (
            select(Review)
            .join(Booking, Review.booking_id == Booking.id)
            .where(Booking.provider_id == provider_profile_id)
            .where(Review.reviewer_id == Booking.customer_id)
        )
        total = await self._db.scalar(select(func.count()).select_from(base_q.subquery()))
        rows = (await self._db.execute(
            base_q.order_by(Review.created_at.desc())
            .offset((page - 1) * page_size).limit(page_size)
        )).scalars().all()
        return list(rows), total or 0
```

## Key Architecture Decisions — Do Not Second-Guess These

1. **Reviews are scoped to completed bookings only.** A `COMPLETED` status check in `ReviewService.create()` is the enforcement point. Do not add an alternative path for reviews without a booking.

2. **`ProviderProfile.rating` and `review_count` are denormalized.** They are recomputed via `_recalculate_provider_rating()` after every new review. This avoids an aggregate subquery on every search result row. The trade-off (slight staleness on concurrent inserts) is acceptable at this scale.

3. **Only customer→provider reviews affect the provider's public rating.** Provider→customer reviews exist in the data model for internal trust signals but are not surfaced in the public `rating`/`review_count` fields. The `_recalculate_provider_rating` query filters `WHERE reviewer_id = booking.customer_id` explicitly.

4. **React Admin uses `Content-Range` headers, not a JSON envelope.** `ra-data-simple-rest` reads `Content-Range: resource start-end/total` from the response header for pagination — it does NOT look at the response body for a total count. Every admin list endpoint must set this header. The `Access-Control-Expose-Headers: Content-Range` header is also required so browsers don't strip it.

5. **Analytics are gated by `subscription_tier` at the router dependency level.** The gate is a FastAPI dependency (`require_pro_or_premium`), not a check inside the service. Services must remain tier-agnostic — the service just computes data, the router decides who may call it.

6. **Search caching uses a 30-second TTL with no explicit invalidation.** Provider availability changes (new bookings, profile updates) do not flush the search cache. Stale-for-30s is acceptable for a marketplace search. Do not add cache invalidation logic — the complexity is not worth it at this scale.

7. **`locust` goes in `requirements-dev.txt`, not `requirements.txt`.** Load testing tools must never be in the production image. If `requirements-dev.txt` does not exist, create it.

8. **Admin auth uses the same JWT as the main app.** There is no separate admin login. The `_admin_only` dependency checks `user.role == ADMIN`. A dedicated admin login UI is deferred to Phase 4 — for now, an admin creates their JWT via the standard auth flow.
